5.1 Introduction
This chapter presents the implementation approach, prototype workflow, testing strategy and result-evaluation
framework for HavenSec Arena. The previous chapters established the problem, reviewed related systems,
selected the AI-assisted multi-agent approach and defined the proposed architecture, modules, technology stack
and development methodology.
The implementation is organized around a controlled simulation lifecycle: scenario initialization, sandbox
preparation, Red Team simulation, event and telemetry generation, Blue Team detection and response, Referee
evaluation, incident-timeline construction and report generation. The design maintains a strict boundary between
simulated activity and real-world infrastructure.
The objective of implementation is not to perform unrestricted offensive activity. Instead, the prototype should
demonstrate that a repeatable cybersecurity exercise can be coordinated, observed and evaluated using synthetic
data and isolated resources.

5.3 Implementation of Major Modules
5.3.1 Scenario Management Module
The Scenario Management Module is the entry point for an exercise. It accepts the scenario type, difficulty level,
objectives and sandbox configuration, then creates the initial simulation state. The resulting context is passed to
the Orchestrator so that all participating components operate against the same scenario definition.
  Select a predefined cybersecurity scenario.
  Set difficulty and simulation objectives.
  Prepare synthetic resources and initial state.
  Assign the scenario context to the participating agents.
 5.3.2 Orchestrator Module
The Orchestrator controls the exercise lifecycle. It initializes the participating agents, maintains scenario state,
sequences permitted simulation actions and provides controlled communication between the Scenario Manager,
Red Team, Blue Team, Referee and reporting components.
5.3.3 Red Team Simulation Module
The Red Team module represents attacker behaviour through controlled simulation. Its actions are restricted to the
selected scenario and sandbox. Reconnaissance, path planning and simulated execution may be represented as
events rather than unrestricted interaction with real systems.
5.3.4 Blue Team Defense Module
The Blue Team consumes telemetry generated by the sandbox. It analyzes suspicious events, records detection
time and performs or recommends predefined defensive actions. Containment and recovery information are
retained for subsequent evaluation.
5.3.5 Referee and Scoring Module
The Referee evaluates the exercise independently of the simulated attacker and defender. It uses timestamped
events and recorded actions to derive detection time, containment, simulated damage and recovery indicators.
These values are combined using a predefined scoring model.
5.3.6 Timeline and Reporting Module
The reporting layer orders timestamped events and agent actions into an incident timeline. It combines the timeline
with evaluation metrics to produce findings, observations and improvement recommendations.

5.6 Event Processing Sequence
A simulation event is treated as a traceable unit of activity. The event should contain enough information to
determine what happened, when it happened and which component generated or consumed it. The minimum
useful fields are an event identifier, scenario identifier, timestamp, source, event type and descriptive details.
  Event creation: a permitted simulated action generates an event.
  Timestamping: the event is assigned a consistent simulation timestamp.
  Telemetry routing: relevant information is forwarded to the Blue Team.
  Response recording: detection and response actions are stored.
  Evaluation: the Referee links actions and outcomes to measurable metrics.
  Reporting: the timeline and final findings are generated from recorded data.

5.11 Proposed Composite Scoring Model
For prototype evaluation, the resilience score can be represented as a weighted normalized combination of the
selected indicators:
Composite Score = w■(Detection Performance) + w■(Containment) + w■(Recovery) + w■(Damage
Control)
The weights should satisfy w■ + w■ + w■ + w■ = 1.0. Detection performance and damage control may require
inverse normalization because lower detection time and lower simulated damage represent better outcomes.

5.16 Implementation Limitations
The prototype remains subject to the limitations identified in the earlier chapters. Scenario realism and scenario
quantity are constrained by available development time and resources. Synthetic data cannot reproduce every
characteristic of enterprise telemetry, and a simplified sandbox may not represent the complexity of a production
environment.
The AI component may assist with reasoning and orchestration, but it should not be treated as an autonomous
authorization mechanism for real-world offensive activity. AI-generated decisions require validation and must
remain subject to the simulation controller and safety boundaries.
Because the available project material contains architecture and validation plans rather than production-scale
benchmark data, performance claims should only be made after actual controlled benchmark runs are recorded.
5.17 Traceability and Reproducibility
A repeatable academic prototype requires each run to have a stable scenario definition, controlled initial state,
timestamped events and a fixed scoring configuration. Reproducibility is strengthened when the same scenario
can be reset and executed again without changing the evaluation criteria.
  Assign a unique identifier to each scenario run.
  Record the scenario configuration before execution.
  Capture timestamps for generated events and responses.
  Preserve the evaluation parameters used for scoring.
  Store the final report together with the corresponding run evidence.

5.19 Acceptance Criteria
The prototype can be considered functionally ready for academic demonstration when the following conditions are
satisfied:
  A scenario can be selected and initialized consistently.
  The sandbox can be created using synthetic or dummy data.
  Red Team, Blue Team and Referee components can participate in one controlled workflow.
  Simulation events are timestamped and traceable.
  Blue Team detection and response are recorded.
  Referee metrics are calculated from recorded evidence.
  A repeatable resilience score is produced using fixed scoring rules.
  The incident timeline and report are generated from the same exercise data.
  Isolation testing demonstrates that the exercise does not depend on live targets or uncontrolled infrastructure.

5.23 Final Conclusion of Chapter
HavenSec Arena can be evaluated as a controlled academic cyber-resilience prototype by demonstrating a
repeatable simulation-to-evaluation workflow while maintaining a strict sandbox boundary. The implementation
framework presented here provides the structure required to convert the proposed architecture into verifiable
evidence.
No unsupported numerical benchmark has been introduced in this chapter. The final project version should replace
the validation placeholders with actual observations, execution logs, screenshots and measured results. Where
implementation differs from the proposed architecture, those differences should be documented explicitly.
Submission guidance: Before final printing, replace every “To be validated”, “[value]”, “[Name]” and “[finding]”
placeholder with evidence from the actual prototype. This keeps the report technically defensible and aligned with the
demonstrated system.
